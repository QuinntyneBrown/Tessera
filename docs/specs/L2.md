# L2 - Detailed Requirements

These requirements describe the production `@tessera/scorm-player` component. The HTML mock in `docs/mocks/scorm-player/` is a design reference, not a source of SCORM behavior. The applicable ADL SCORM 1.2 and SCORM 2004 2nd, 3rd, and 4th Edition specifications define the protocol and data-model rules referenced below. The host LMS supplies learner authorization, an opaque attempt identity, course delivery, and durable storage. ADL's [SCORM 1.2 documentation](https://adlnet.gov/assets/uploads/SCORM_1_2_pdf.zip), [SCORM 2004 3rd Edition documentation](https://adlnet.gov/assets/uploads/SCORM.2004.3ED.DocSuite.zip), and [SCORM 2004 4th Edition documentation](https://adlnet.gov/assets/uploads/SCORM_2004_4ED_v1_1_Doc_Suite.zip) are reference sources; the specification for the detected edition is authoritative for its behavior.

**Extracted-course input assumption:** The host supplies the URL of `imsmanifest.xml` and serves every asset referenced by that manifest. A launch-page URL alone does not provide enough information to identify the SCORM version, resource tree, or sequencing rules.

## L2-001: Supported course inputs
**Traces to:** L1-001

The player must accept either a SCORM ZIP package or an extracted course manifest URL through its documented input interface. It must identify SCORM 1.2 or SCORM 2004 2nd, 3rd, or 4th Edition before launch.

**Acceptance Criteria:**
1. Given a valid ZIP for each supported version, when the host loads it, then the player identifies that version and displays the course title and available activities.
2. Given a valid extracted manifest and its assets, when the host supplies the manifest URL, then the player identifies the same version and activities as for the equivalent ZIP.
3. Given an unsupported or unidentifiable version, when loading finishes, then launch is refused and the player reports the version problem in text.

---

## L2-002: ZIP and manifest validation
**Traces to:** L1-001

The player must validate the archive, root manifest, launch references, and package structure before launching content. Package size, expanded size, and entry-count limits must be configurable by the host and enforced before or during extraction.

**Acceptance Criteria:**
1. Given a ZIP without a root `imsmanifest.xml`, when it is loaded, then the player rejects it and names the missing manifest.
2. Given malformed XML, a missing launch resource, or a resource path escaping the package root, when the package is loaded, then the player rejects it without executing course content.
3. Given a ZIP that exceeds any configured archive, expanded-size, or entry-count limit, when it is loaded, then processing stops and the player reports which limit was exceeded.

---

## L2-003: Extracted-course validation
**Traces to:** L1-001

For an extracted course, the player must resolve launch resources relative to the manifest URL and fail clearly if the manifest or a selected activity cannot be loaded.

**Acceptance Criteria:**
1. Given a manifest with a relative launch path, when the learner opens that activity, then the player requests the resource under the manifest's course root.
2. Given a missing or unreadable manifest, when loading begins, then the player shows a recoverable loading error and does not start a runtime session.
3. Given an activity whose launch resource returns an error, when the learner opens it, then the player reports the failed activity and offers a retry without marking it complete.

---

## L2-004: Activity launch
**Traces to:** L1-002

The player must launch the resource selected by the manifest and make the edition-specific SCORM API available before a sharable content object (SCO) runs. Each runtime session must belong to one SCO and one learner attempt.

**Acceptance Criteria:**
1. Given a valid single-SCO course, when launch begins, then its manifest-designated resource opens and can discover the correct API object before calling initialize.
2. Given a multi-SCO course, when the learner moves to another SCO, then the previous SCO session ends and a distinct session starts for the newly selected SCO.
3. Given an asset rather than a SCO, when it opens, then it is displayed without requiring SCORM runtime calls.

---

## L2-005: Learner navigation
**Traces to:** L1-002

The player must expose the activities the learner may currently choose and support previous and next navigation where the course rules permit it.

**Acceptance Criteria:**
1. Given a SCORM 1.2 course with multiple launchable items, when the learner chooses an item, then the player opens that item's resource and updates the current position.
2. Given the first or last available activity, when the player shows navigation controls, then unavailable previous or next actions are disabled and their state is conveyed to assistive technology.
3. Given an activity that is unavailable under the current course rules, when the learner views the outline, then it is identified as unavailable and cannot be launched through the player controls.

---

## L2-006: SCORM 2004 sequencing and navigation
**Traces to:** L1-002

For each supported SCORM 2004 edition, the player must apply the edition's sequencing and navigation rules, including choice and flow controls, attempt limits, objective rules, and rollup, rather than using a fixed lesson order.

**Acceptance Criteria:**
1. Given a course that disallows choice and requires flow, when the learner tries to select a later activity, then the player blocks that selection and permits the next activity selected by the sequencing rules.
2. Given a SCO that makes a valid SCORM navigation request, when its session ends, then the player processes that request and launches the resulting activity or ends the attempt as specified by the course.
3. Given a course with an attempt limit or objective-based prerequisite, when the learner reaches that rule, then available activities and course rollup match the applicable edition's specified result.

---

## L2-007: SCORM 1.2 API
**Traces to:** L1-003

For SCORM 1.2 SCOs, the player must expose the `API` object and implement the eight `LMS*` methods, their string return values, session states, and error reporting according to SCORM 1.2.

**Acceptance Criteria:**
1. Given a SCORM 1.2 SCO, when it finds `API` and calls `LMSInitialize("")`, then the call succeeds and the SCO can read and write supported data elements.
2. Given an invalid call sequence or parameter, when the SCO calls an API method, then the method returns the specified failure value and `LMSGetLastError()` reports the corresponding SCORM 1.2 error code.
3. Given a successfully initialized session, when the SCO calls `LMSFinish("")`, then its final valid state is submitted and later calls obey the terminated-session rules.

---

## L2-008: SCORM 2004 API
**Traces to:** L1-003

For SCORM 2004 SCOs, the player must expose `API_1484_11` and implement `Initialize`, `Terminate`, `GetValue`, `SetValue`, `Commit`, `GetLastError`, `GetErrorString`, and `GetDiagnostic` according to the identified edition.

**Acceptance Criteria:**
1. Given a supported SCORM 2004 SCO, when it finds `API_1484_11` and calls `Initialize("")`, then the call returns the edition-specified success string and the SCO can use its data model.
2. Given a duplicate initialization, a call after termination, or a nonempty argument where an empty one is required, when the SCO calls the API, then the return value and last error match that edition's specification.
3. Given the same course behavior under 2nd, 3rd, and 4th Edition fixtures, when an edition-specific rule differs, then the player applies the rule for the identified edition.

---

## L2-009: Runtime data models
**Traces to:** L1-003

The player must enforce each edition's required data elements, read/write rules, vocabulary, range and length limits, and element-specific error codes. It must not silently accept invalid values.

**Acceptance Criteria:**
1. Given an initialized SCO, when it writes and then reads a valid writable element, then the read returns the value in the form required by that edition.
2. Given a read-only element, when the SCO attempts to write it, then the write fails and the specified error is available through the API.
3. Given an out-of-range score, invalid status vocabulary, or over-limit suspend data, when the SCO writes it, then the write fails without changing the previous valid value.

---

## L2-010: Runtime session lifecycle
**Traces to:** L1-003

The player must preserve valid SCO changes through commit, termination, and activity changes, and must prevent one SCO from manipulating another SCO's live runtime session.

**Acceptance Criteria:**
1. Given uncommitted valid changes, when the SCO calls its edition's commit method, then the current SCO state is submitted to the host persistence boundary.
2. Given valid changes followed by termination, when the session ends, then the final state is submitted even if the SCO did not make a separate commit call.
3. Given an ended SCO session, when a later call targets its API object, then the call fails with the edition-specific session error and does not change the new SCO's state.

---

## L2-011: Resume an attempt
**Traces to:** L1-004

The player must restore the saved state for the same course, learner attempt, and SCO without mixing it with another attempt.

**Acceptance Criteria:**
1. Given a saved attempt containing lesson location and suspend data, when that attempt is reopened, then the SCO reads those saved values and the player returns to the saved activity when course rules permit.
2. Given a new attempt for the same learner and course, when it starts, then prior attempt state is absent unless the host explicitly supplies it for that new attempt.
3. Given two learners opening the same course, when either learner resumes, then each receives only the state supplied for their own attempt.

---

## L2-012: Progress and outcomes
**Traces to:** L1-004

The player must derive status, completion, success, and score from edition-specific SCO data and course rollup rules. It must identify unknown outcomes instead of inventing completion or a percentage.

**Acceptance Criteria:**
1. Given a SCORM 1.2 SCO that reports `completed` with a score, when its state is accepted, then the player reports the corresponding lesson status and score to the host.
2. Given a SCORM 2004 SCO that reports completion and success separately, when its state is accepted, then the player reports both outcomes separately.
3. Given a course that has not reported enough data to calculate overall completion, when progress is shown, then the player presents an unknown or in-progress state rather than a fabricated percentage.

---

## L2-013: Host persistence boundary
**Traces to:** L1-005

The component must document the host inputs and callbacks for loading attempt state, saving SCO state, and receiving outcome and error events. A save failure must remain visible and retryable without discarding the unsaved state.

**Acceptance Criteria:**
1. Given a valid SCO commit, when the host save succeeds, then the player acknowledges the saved state and emits the updated outcome once.
2. Given a host save failure, when a commit or termination submits state, then the player retains the latest state, announces that progress was not saved, and offers retry.
3. Given a retry after a failed save, when the host accepts the state, then the error clears and the submitted state matches the latest SCO values.

---

## L2-014: Host identity and authorization
**Traces to:** L1-006

The host LMS must authorize course access and supply an opaque attempt context before the player loads content. The player must never treat an identifier or claim from course content as authority to switch learners, courses, or attempts.

**Acceptance Criteria:**
1. Given no authorized attempt context, when the host attempts to launch a course, then the player refuses launch and emits an integration error.
2. Given a SCO that reports a different learner or course identifier, when it writes runtime data, then the player's persistence calls remain bound to the host-supplied attempt context.

---

## L2-015: Untrusted content isolation
**Traces to:** L1-006

The player must run course content in an isolated execution context that cannot read host credentials, other learner attempts, or arbitrary host application state. The host must provide a delivery origin and runtime bridge that preserve SCORM API access without granting course content direct access to the LMS application.

**Acceptance Criteria:**
1. Given a course script that attempts to read the host application's DOM, cookies, or storage, when it runs, then browser isolation prevents access.
2. Given a course script that attempts to send a forged runtime message for another attempt, when the bridge receives it, then the message is rejected and no host state changes.
3. Given a host configuration that cannot provide the required isolation and API access, when launch is attempted, then the player refuses launch with a clear integration error.

---

## L2-016: Input and data protection
**Traces to:** L1-006

The player must validate package paths, runtime values, and bridge messages, and must keep learner data out of URLs, console output, and diagnostic events unless explicitly required for the host callback contract.

**Acceptance Criteria:**
1. Given a package path containing traversal syntax or an unexpected external origin, when the player resolves it, then the resource is rejected before it can execute.
2. Given a malformed or oversized bridge message, when it arrives, then the player rejects it without changing SCO or learner state.
3. Given an error involving suspend data or a score, when diagnostics are emitted, then they contain an error category and attempt correlation token but not the learner identifier or raw runtime value.

---

## L2-017: Keyboard and screen reader operation
**Traces to:** L1-007

The player controls must use semantic roles, visible focus, predictable focus movement, and text status announcements. Player-owned interactions must satisfy WCAG 2.2 AA and the applicable WAI-ARIA Authoring Practices.

**Acceptance Criteria:**
1. Given keyboard-only use, when the learner navigates the outline, launches an allowed activity, retries an error, and exits, then every player action is operable without a pointer and focus remains visible.
2. Given a screen reader, when the current activity, progress, save status, or error changes, then its name or status is announced without requiring the learner to search the page.
3. Given a blocked or unavailable navigation action, when the learner encounters it, then its state and reason are available as text and through assistive technology.
4. Given a component change, when accessibility verification is performed, then automated checks pass and manual checks cover JAWS, NVDA, VoiceOver, TalkBack, and Narrator on their supported platforms.

---

## L2-018: Responsive player layout
**Traces to:** L1-008

The player shell and its own controls must remain fully usable at extra-small, small, medium, large, and extra-large viewport widths, at up to 400% browser zoom, and with enlarged text or increased text spacing, without horizontal page scrolling or loss of content or functionality caused by player chrome.

**Acceptance Criteria:**
1. Given viewport widths of 320, 576, 768, 992, 1200, and 1920 pixels, when the player is opened, then its outline, status, content frame, and controls remain readable and operable without horizontal page scrolling from the player shell.
2. Given a narrow viewport, when the learner opens the course outline, then it can be expanded, used, and collapsed by keyboard and screen reader.
3. Given a viewport resize during an attempt, when the layout changes, then the active SCO and unsaved runtime state are preserved.
4. Given a 1280 by 1024 pixel window at 400% browser zoom, when the player is opened, then its outline, status, content frame, and controls reflow into a single column, remain readable and operable, and cause no horizontal page scrolling from the player shell (WCAG 2.2 SC 1.4.10).
5. Given player text enlarged to 200% without page zoom, when the player is opened, then no player text or control is clipped, truncated, or overlapping (WCAG 2.2 SC 1.4.4).
6. Given line height 1.5, paragraph spacing 2, letter spacing 0.12, and word spacing 0.16 times the font size applied to player text, when the player is opened, then no player content or functionality is lost (WCAG 2.2 SC 1.4.12).
7. Given a zoom level change during an attempt, when the layout changes, then the active SCO and unsaved runtime state are preserved.

---

## L2-019: Loading performance and responsiveness
**Traces to:** L1-008

The player must show its shell promptly, keep its controls responsive during package processing, and communicate loading progress. Course-authored content load time is outside the player-shell target.

**Acceptance Criteria:**
1. Given a local test fixture with an extracted manifest and a warm application bundle, when launch begins in Chromium at 4× CPU slowdown, then the player shell and loading status render within 2 seconds in at least 95 of 100 measured runs.
2. Given a 50 MB ZIP fixture within configured limits, when it is processed, then the player shows a loading or processing state and its Cancel control responds within 200 milliseconds under the reference test conditions.
3. Given a cancelled package load, when cancellation completes, then no SCO is launched and the player can accept another source.

---

## L2-020: Recoverable failures and diagnostics
**Traces to:** L1-008

The player must distinguish loading, runtime, and persistence failures; show the learner an actionable message; and send the host a machine-readable error category without exposing private learner data.

**Acceptance Criteria:**
1. Given a manifest fetch failure, when loading ends, then the learner sees a retry action and the host receives a loading error category.
2. Given a SCO runtime failure, when the player detects it, then the current attempt remains identifiable and the host receives a runtime error category.
3. Given a persistence failure, when the learner attempts to leave, then the player warns that progress is unsaved and offers retry before ending the attempt.

---

## L2-021: Angular library integration
**Traces to:** L1-005

The player must be consumable as the standalone `@tessera/scorm-player` Angular package. Its documented public interface must let an LMS provide either supported course source, the authorized attempt context, the host persistence functions, and receive state and error events. Browser support is required; server-side rendering is not required.

**Acceptance Criteria:**
1. Given a separate Angular LMS application with the package installed, when it imports the player and supplies an extracted course source and host callbacks, then a learner can launch the course and the host receives state updates.
2. Given the same application with a ZIP source, when the host supplies the required course-delivery integration, then the learner can launch the course through the same component interface.
3. Given a host that omits a required attempt or persistence input, when it initializes the player, then initialization fails with a documented integration error before course content runs.
