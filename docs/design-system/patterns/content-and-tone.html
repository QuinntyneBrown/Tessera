Pattern

Content and tone

Learners use Tessera in the middle of a course, often in a hurry and sometimes with a screen reader. Copy is calm, plain and specific, and the heading, body and buttons of one view read as a single sentence of intent.

Overview

The voice is a helpful course assistant: direct, warm without being chatty, and never blaming. Three principles apply to every string.

  • Plain. Everyday words, short sentences, one idea per sentence. "Learners could not be loaded", not "Failed to retrieve learner entities".
  • Specific. Name the thing: "Retry save", "Remove Ada Lovelace", "Locked until “Ask better questions” is complete."
  • Reassuring. Say what is safe before asking for anything: "Your selections are safe." "Your latest progress is kept on this page."

This page is about composition: how a heading, a notice, a dialog and its buttons work together. Field-level rules live on forms; empty and error copy formulas on empty and error states.

When to use

Apply these rules to every string a learner or administrator sees or hears, including aria-labels, live-region announcements, tooltips and the reason text beside unavailable controls. Course content inside a SCORM package is the author's, not Tessera's; the player chrome around it follows these rules.

Structure

A view reads top to bottom as context, then status, then task, then action. The page header names the task; a notice interrupts only with something the learner must know; the buttons repeat the verb of the heading so the outcome is never a surprise.

Workplace safety essentials

Assign learners

Required learning · 35 minutes · Due 31 October 2026

3 learners already assigned

They keep their current due date. Assigning them again changes nothing.

Remove 3 learners?

Ada Lovelace, Grace Hopper and Alan Turing will lose access to Workplace safety essentials. Their progress so far is kept.

Heading names the task, the notice states a fact and what is safe, the dialog heading asks the question its danger button answers.

Heading hierarchy

  • One h1 per page, from the host LMS or the page header. Components never render an h1; the SCORM player's course title, activity heading and notices take the level the host passes (the mocks use h2 for the course and h3 for the activity and notices).
  • Notice and dialog headings are real headings, so screen reader users can jump to them, and they name the region through aria-labelledby.
  • Eyebrows ("Workplace safety essentials") are paragraphs, not headings; they give context, not structure.

Responsive behaviour

  • Write for 320px first. A button label that wraps at 320px is too long; shorten the verb phrase rather than truncating.
  • Never truncate errors, hints, reasons or headings. Only chip labels and long names truncate, and then the full text is available in a tooltip on hover and on remove-button focus.
  • Do not write different copy per breakpoint. If a phone layout hides text (the outline becomes "Show outline"), the hidden content stays reachable, and the toggle label says what it reveals.
  • German and Finnish run about 30% longer; leave room by keeping English short, not by fixing widths.

Accessibility

Role and pattern

Copy carries meaning that colour and icons only repeat. See Understanding 2.4.6 Headings and Labels, Understanding 2.5.3 Label in Name and Understanding 4.1.3 Status Messages.

Keyboard

KeyWhat the copy must support
TabEach focus stop has a name that makes sense out of context: "Remove Ada Lovelace", not "Remove".
Enter, SpaceThe button label predicts the result; a danger button names the loss ("Remove 3 learners").
EscDialogs say what Esc keeps: the safe button ("Keep learners") is the Esc result.

Focus

When focus moves to a heading (a dialog title, a notice, "Stream ended"), that heading is the announcement, so it must make sense alone. Do not repeat it in a live region at the same time.

Labelling

The accessible name starts with the visible label (label in name). Icon-only controls use verb + object. Live announcements are short, end with a full stop, and are joined rather than overwritten when several arrive together ("Ask better questions complete. Progress saved.").

Motion

Text never animates in letter by letter or scrolls as a marquee. Changing values (the elapsed time on the LIVE badge) are hidden from screen readers; milestones are announced instead.

Touch

Short labels keep buttons on one line at 44px; two words fit side by side in a sheet footer at 320px.

Content

Sentence case

Capitalise only the first word and proper nouns, everywhere: headings, buttons, tabs, menu items. "Preview assignment", "Course outline", "Lecture hall A". Uppercase is a style (text-transform on eyebrows and the LIVE badge), never typed into the string, so screen readers do not spell it out.

Button verbs

  • Start with a verb and name the object when the view does not: Retry, Retry save, Load more results, Preview assignment, Exit course, Clear all selections, Show outline.
  • Pair opposites consistently: Show / Hide, Mute / Unmute, Add / Remove, Exit / Continue.
  • Never: OK, Yes, No, Submit, Click here, Confirm. In a confirmation, the buttons are the two outcomes ("Keep learners", "Remove 3 learners").

Numbers, dates and durations

  • Numerals for all counts, including at the start of an announcement: "6 more results loaded.", "3 learners selected". Pluralise correctly; never "learner(s)".
  • Position: "Activity 2 of 4". Ranges: "6 of 24 learners".
  • Dates: day month year with the month in words, "31 October 2026"; "Today" and "Yesterday" only in lists. Times: 24-hour from the locale, "10:42".
  • Durations in prose: "35 minutes", "48 minutes", "1 hour 5 minutes". Clocks (00:48:12) only for elapsed time on screen; announce them in words: "It was live for 48 minutes."
  • Units with a space: "10 seconds behind live", "5 s" only in technical tables.

Error message formula

What happened + what is safe or why + what to do. "Learners could not be loaded. Your selections are safe." + Retry. "You don’t have access to this stream. Sign in again or ask the organiser." Never blame ("You entered an invalid…"), never apologise more than once, never show only a code.

Punctuation

  • Use the ellipsis character (…) for ongoing work; curly quotes and apostrophes (“Zed”, can’t); a middle dot (·) to separate metadata.
  • No exclamation marks, no emoji, no "please" in errors.

Drift fixed during extraction:
