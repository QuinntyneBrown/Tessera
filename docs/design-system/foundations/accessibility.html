Foundation

Accessibility

Every learner has to be able to finish the course. Tessera components work with JAWS, NVDA, VoiceOver, TalkBack and Narrator, are fully operable by keyboard alone, and conform to WCAG 2.2 AA at minimum. This page lists what that means in practice and how each change is checked.

Overview

Accessibility is built into the tokens and classes rather than added per page:

  • Every text and control colour pair is checked at 4.5:1 or 3:1 in both themes (colour).
  • One amber focus ring, 3px with a 2px gap, on every focusable element.
  • 44px controls by default; nothing smaller than 24px.
  • Disabled controls keep readable text and show a dashed edge; they are never shown by fading alone.
  • Motion tokens collapse under reduced motion (motion); forced colours hand control to system colours (theming).
  • Native elements first; ARIA only where the WAI-ARIA Authoring Practices pattern needs it.

Commitments

The WCAG 2.2 AA success criteria that shape component design, and the rule Tessera follows for each.

Every component must be fully functional with all five major screen readers. These are the combinations each release is verified on:

Target sizes

--target-min --target-comfortable Ada Lovelace
24px minimum (WCAG 2.5.8) and 44px comfortable; the chip remove button (28px) and icon button (44px) in context.
TokenValueUse
--target-minThe floor for every target: chip remove buttons, inline links in dense rows, navigation summaries.
--target-comfortableThe default for buttons, fields, toggles and media controls; every primary action on touch.

Targets smaller than 44px sit where nothing else crowds them: a 24px circle centred on each small target must not overlap another target.

Focus ring

Ring on surface
Ring on canvas
  • Shape: a solid outline of --focus-ring-width (3px) in --color-focus-ring, drawn --focus-ring-offset (2px) outside the element, following its radius.
  • When: on :focus-visible only, so a mouse click does not leave a ring but keyboard focus always shows one.
  • Colour: amber, never the brand teal, so it stays distinct from primary fills, selected options and the current lesson. Light uses --palette-orange-600, dark --palette-orange-300.
  • On media: video controls on the dark scrim use --color-media-focus-ring (light amber in both themes).
  • Composite widgets: the combobox draws the ring on the whole field while its input has focus; the active option gets a 2px accent outline inside the list, which is a different thing from focus.
  • Forced colours: the ring becomes Highlight.
  • Where an outline cannot show (clipped containers), use --shadow-focus, which draws the same 2px gap and 3px ring as a box shadow.
TokenValueUse
--focus-ring-widthOutline thickness on every focusable element.
--focus-ring-offsetGap between the element and the ring.

Control heights

Small, medium (default) and large buttons. Fields and selects use medium.
TokenValueUse
--control-height-smChips, inline icon buttons inside a field, small buttons in a status row.
--control-height-mdDefault for buttons, text fields, selects and the combobox field (the combobox mock's 40px field was raised to match).
--control-height-lgA single hero action.

Heights are minimums (min-height). With 200% text a control grows taller rather than clipping its label.

Component contract

Every component page's Accessibility section answers these seven points, and every component change ships with an accessibility test: automated checks plus manual screen reader verification.

  1. Role and pattern: the native element or WAI-ARIA pattern used, linked to the APG pattern.
  2. Keyboard: a table of every key and its effect (Tab, Shift+Tab, Enter, Space, Esc, arrows, Home/End, type-ahead).
  3. Focus: where focus starts, where it goes when something closes or disappears, and how the ring looks.
  4. Labelling: what must be labelled, how, and what is announced (including live-region messages).
  5. Contrast: the token pairs involved, with live ratios in both themes.
  6. Motion: what animates and what happens under reduced motion.
  7. Touch: target sizes and the alternative to anything hover-only.

Testing procedure

Automated, on every change

  • Playwright acceptance tests in Chromium only, using page objects that own every selector. They cover keyboard operation, focus movement, names and states, announcements, 320px reflow, 200% text, text spacing, forced colours and reduced motion (emulated).
  • axe checks scoped to the component, in both themes and every state. Zero violations is necessary, not sufficient.
  • Contrast: every pair in tokens/contrast-pairs.json, both themes.

Manual, before release

  1. Tab through every state of the component with no mouse. Every action must be reachable, the ring always visible, and focus never lost.
  2. Run each screen reader row above, one screen reader at a time, and listen: names, roles, states, descriptions and live announcements must be correct and timely. Capture transcripts where possible (NVDA Speech Viewer).
  3. Check widths, actual 200% and 400% browser zoom, 200% text and text-spacing overrides (see responsive).
  4. Turn on a Windows contrast theme and the platform's reduced-motion setting; confirm focus, selected, active and disabled states stay distinguishable.
  5. On iOS and Android, check reading order, touch targets and the real on-screen keyboard.
  6. Record each row as passed, failed (with a defect) or "Not run" with the reason. Emulation is labelled as emulation.

Step-by-step instructions, scenario URLs and the override scripts are in the manual screen reader verification guide.
