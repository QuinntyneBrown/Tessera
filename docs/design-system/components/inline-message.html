Inline message

An inline message is one short line of guidance or feedback tied to a single field: how to fill it in, what is wrong with it, or that it checked out. It lives directly under the field and is read with it.

Overview

Use an inline message for anything that concerns one control: a hint ("Select one or more learners"), a validation error ("Select at least one learner"), a confirmation that a value was accepted, or a soft warning that does not block submission. The form field wrapper places it; this page defines the message itself.

  • Hint (.message): neutral, muted, always present when the field needs explaining.
  • Error (.message--error): icon + text, shown after validation, directly below the field and before the hint.
  • Success (.message--success): icon + text, for checks the person would otherwise wonder about ("Course code is available").
  • Warning (.message--warning): icon + text, for a valid but risky value ("Due date is on a weekend").

For a condition that affects a whole form or region, use an alert; for an error summary at the top of a long form, see the forms pattern. For feedback about an action, use a toast.

Anatomy

  1. Status icon (error, success, warning)16px, aria-hidden="true", aligned to the first line with --space-0-5. Hints have no icon.
  2. Message text--text-body-sm (14px), tone colour. One sentence that names the fix.
  3. HintMuted --color-fg-muted. Stays visible when an error appears; the error goes above it.

Spacing: --space-2 (8px) between the field and the first message and between messages, set by the .field gap; --space-2 between icon and text.

Variants

Six characters, for example COM-101.

Hint, error (with hint kept), success, warning. Each message is in the field's aria-describedby.

In a group

For a checkbox or radio group, the message belongs to the <fieldset> and sits under the legend's options, referenced from the fieldset with aria-describedby.

Notify learners by

Choose at least one way to notify learners.

Sizes

Inline messages use one size (14px body-small); they follow the field's width.

States

A message is not interactive. It appears with its field in every field state; the field's own states come from text field. Pointer and focus states are forced with data-state.

Timing

  • Errors appear on blur or on submit, never while the person is still typing the first time. Once shown, they re-validate on input and disappear as soon as the value is valid.
  • Success appears only after an asynchronous check finishes (availability, enrolment); a spinner (.loading-inline) stands in while it runs.
  • Hints never change with validation state.

Responsive behaviour

  • The message takes the field's full width and wraps; it never truncates and never sits beside the field, even on wide screens.
  • The icon stays aligned to the first line as the text wraps (align-items: flex-start).
  • In .field__below the hint shares a row with a counter or a text button ("Clear all selections"); below about 20rem the button wraps to its own line, end-aligned.
  • 200% text and text-spacing overrides only make the message taller.

Theming

The message reads only the status foreground tokens: --color-fg-muted (hint), --color-danger-fg, --color-success-fg, --color-warning-fg. The icon inherits the text colour. There are no component tokens; to re-skin, override the semantic tokens on a wrapper. In dark theme the foregrounds lighten to the 200–300 steps of each ramp. In the shipped combobox the error colour is --t-combobox-error, fed by --t-colorPaletteRedForeground1; see theming.

Accessibility

Role and pattern

A plain <p> referenced by the control's aria-describedby; no role. The field sets aria-invalid="true" while an error is shown. List the error id before the hint id so the error is read first, matching visual order. See Understanding 3.3.1 Error Identification.

Keyboard

KeyAction
TabMoves to the field; the message is read as the field's description. Messages are never tab stops.
(none)A message contains no controls. If a fix needs an action, put a button next to the field, not inside the message.

Focus

On submit with errors, focus moves to the first invalid field (or to the error summary in long forms); its description then reads the error. Showing an error on blur does not move focus.

Labelling

Errors are not announced by a live region on blur; they are read when the person returns to the field. Components that validate asynchronously (the combobox) announce the result in their own polite live region. Errors name the field or the fix in words, so "Error" is never the only cue; the icon is aria-hidden.

Motion

None. Messages appear and disappear in place; no slide or shake.

Touch

Messages are not targets. Keep them out of the field's tap area so a tap on the message does not trigger anything; a text button in .field__below keeps its own 24px minimum target.

Content

  • Errors say how to fix it: "Select at least one learner.", "Enter a course code like COM-101." Not "Invalid input" or "Required".
  • Hints describe what a good answer looks like: "Select one or more learners. Search to narrow the results."
  • Success confirms the specific value: "COM-204 is available."
  • Warnings explain the consequence, not just the fact: "Learners may not see it until Monday."
  • One sentence each, ending with a full stop. Sentence case. No exclamation marks.
  • Mark required fields in the label ("(required)"), so the error is not the first time a person learns the field is required.
